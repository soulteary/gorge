## 合并与发布顺序

1. 合并 Gorge 准备 PR，确认最终 main SHA；核对该源码检查。按固定 SHA 更新
   两仓库的 `PHORGE_CONTRACT_REF` / `GORGE_CONTRACT_REF` 时，重新运行配对工作流。
2. 在干净、同步的 Gorge main 上确认新标签未被使用，创建并推送
   `2026.10.07-r2` 标签。这一步才触发镜像发布与 Go Test Report。
3. 等待 [Release 工作流](../../.github/workflows/release.yml)全部矩阵项成功。
   当前矩阵为 14 个服务，每个固定标签须包含 `linux/amd64` 和 `linux/arm64`；
   以工作流矩阵为最终清单。检查镜像摘要、源码 revision 和实际启动结果。
4. 使用双语发布正文创建 Gorge GitHub Release，保留镜像运行、测试报告链接
   和最终 SHA。Release 工作流仅推送镜像，GitHub Release 正文需单独提交。
5. Gorge 固定标签可用后，再合并 Phorge 准备 PR：它将默认 Gorge 镜像升级为 r2。
   核对 Phorge 合并后源码与 Gorge 最终源码的契约，再创建 Phorge r2 标签及 Release。
6. 在测试环境完成成对升级验收，保存 Phorge 运维工具生成的真实 version-pair
   身份记录。备份持久状态，执行 schema 迁移，检查 capability、执行权和实际业务路径。

示例操作在 Gorge 仓库中执行；先完成上面的源码和检查核对：

```bash
git switch main
git pull --ff-only origin main
git status --short
git rev-parse HEAD
git ls-remote --tags origin refs/tags/2026.10.07-r2
# 仅在工作区干净、远端标签不存在且该提交检查通过后执行：
git tag -s 2026.10.07-r2 -m "Gorge release 2026.10.07-r2"
git push origin refs/tags/2026.10.07-r2
# 等镜像构建及上述核验完成，整理正文准备提示和真实结果后：
gh release create 2026.10.07-r2 --verify-tag \
  --title 2026.10.07-r2 --notes-file RELEASE_NOTES.md
```

Gorge 的 CalVer tag 发布会同时更新各服务的 `*-latest`；它没有独立的镜像晋升
阶段，也不会自动创建 GitHub Release。不要把普通 PR 的检查成功解释为标签发布
或两个架构的实际运行验证。[交付流程](../delivery.md)记录现有行为。
