## 验证记录与边界

本次准备检查包括 `make check`、`make lint`、显式设置配对 Phorge 路径的
`make docs-check`、发布工具负面测试和 `git diff --check`；结果记录在准备 PR。
跨仓库检查的功能基线为上面的两个完整 SHA，准备分支额外包含发布文档和工作流改动。

准备 PR 的远程配对检查使用仓库变量固定功能基线：Gorge 的 `PHORGE_CONTRACT_REF`
取 Phorge 功能截止 SHA，Phorge 的 `GORGE_CONTRACT_REF` 取 Gorge 功能截止 SHA。
这些变量仅选择源码检查对象，不表示新版本已发布；最终合并后重新固定最终源码对。

本次源码与文档检查不替代 tag 工作流的候选镜像构建和完整配对验收。最终门禁要求
必测 MySQL、Redis、S3、Elasticsearch、Meilisearch、图片等阶段真实执行，带用例名的
skip 会失败。十四个镜像都做包装检查，image/render 以候选 digest 运行；其他服务
通过配对源码契约验证。真实浏览器业务、供应商投递、生产性能和生产恢复另行验收。

## 合并与发布顺序

1. 分别合并 Gorge 和 Phorge 发布准备 PR，确认两个最终 main SHA 和检查结果。
   两个 PR 的发布文档可独立合并；部署和正式发布须使用完整源码对。
2. 将 Gorge 的 `PHORGE_CONTRACT_REF` 更新到最终 Phorge SHA，将 Phorge 的
   `GORGE_CONTRACT_REF` 更新到最终 Gorge SHA；用两个完整 SHA 重跑契约工作流。
   手动 dispatch 也可显式提供相同 SHA，不从 main 隐式选择配对源码。
3. 确认 Gorge 工作树干净、最终提交检查通过、新标签未被使用后，创建并推送
   `2026.10.08-r1` tag。tag 触发 [Release](../../.github/workflows/release.yml)及
   Go Test Report；PR 和分支推送不触发正式发布。
4. 等待 Release 的源码对检查、十四个双架构候选构建及完整配对验收全部成功。
   工作流自动以双语正文发布 GitHub Release，附带 `release-manifest.json`；清单绑定
   验收回执的摘要，完整回执保存在该运行的 `paired-release-evidence` 制品中。
   不要另行创建同名 Gorge Release。既有版本禁止覆写，失败状态须先核对再处理。
5. 检查清单中的两个 commit、全部镜像 digest、验收范围与 Release 状态。新流程
   不生成 `服务名-2026.10.08-r1` 或提升 `服务名-latest`；将 digest 写入部署 override。
6. 为已核对的 Phorge 最终源码创建同版本 tag 和 GitHub Release，使用其双语正文，
   链接 Gorge Release 和清单。在临时环境完成成对升级、备份、迁移、执行权和业务验收，
   保留真实 version-pair 记录后再切换生产。

db-api `1.2` 的运行时升级顺序为先升级 Phorge PHP consumer，再升级 db-api 服务，
见 [db-api 兼容说明](../modules/dbapi.md)。先发布 Gorge 产物不表示先切换运行中的
db-api；旧 PHP consumer 不识别新增复制状态标签。

发布工具及失败处理以[发布门禁说明](../../deploy/release/README.md)、
[交付](../delivery.md)和 Phorge 的部署/运维说明为准。
